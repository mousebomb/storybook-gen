# 20260916 接口错误日志加详

## 用户需求

上一轮的失败自动重排队长记后实测，发现失败日志只有一句
`MiMo TTS 失败：HTTP 500 Internal Server Error`——不知道 500 到底为什么，接口返回的详细信息也没打出来。
要求"把日志打印得详细一点"。当时的实际情况：接口持续 500，整批文件都转不出来。

## 先诊断：500 是谁的问题

用最小请求直接打接口复现（4 字文本），逐步排除：

| 变量 | 结果 |
|------|------|
| 同一请求连打 4 次 | 全部 500（不是间歇性抖动的偶发） |
| 换音色（茉莉 / 冰糖 / Mia） | 全部 500 |
| 去掉风格消息、去掉 audio 参数 | 全部 500 |
| 超短文本（4 字）与长文本 | 500 / 连接被中断 |
| 同一 Key 调非 TTS 模型 | 200（能正常返回） |

响应体固定为 `{"error":{"code":"500","message":"Internal Server Error","param":"","type":"InternalServerError"}}`，
响应头 `x-mife-upstream-status: 500`（小米网关转发到上游，上游返回 500）。
全程没有出现 429。

**结论：不是本项目的 bug，也不是限流或额度问题，是 TTS 模型服务端在故障。**
鉴权、网络、额度都正常（非 TTS 模型能返回 200），等接口恢复即可。
也因此这轮没法用真接口跑流程，改用 stub 验证（见下）。

## 改动

1. **`src/errors.ts`（重写）**：`ApiError` 带上 `detail`——状态码/状态文本、响应体原文、错误码、
   关键响应头、请求参数、耗时、按状态码给出的处理建议；`report()` 输出多行诊断文本。
   响应体改用 `text()` 读取后自行 JSON 解析：以前直接 `res.json()`，解析失败就什么原文都没了；
   现在非 JSON 的网关报错页也会原样保留。新增 `truncateBody` / `hintForStatus` /
   `errorSignature` / `errorSummary` / `formatErrorReport`。
2. **`src/errorlog.ts`（新增）**：`FailureLog` 负责日志去重（同类错误 30s 内只完整展开一次）
   与「接口疑似故障」告警，避免一本 200 段的书连续 500 把控制台刷爆。
3. **`src/providers/mimo.ts`**：记录模型/音色/格式/文本长度/风格来源/超时配置与本次耗时；
   4xx（请求本身有问题）额外附 20 字文本片段；「200 但无音频」「响应非 JSON」两种失败也带上响应体原文。
4. **`src/pipeline.ts`**：`SegmentRetryInfo` 由 `error` 字符串改为 `message` + `err` 对象
   （日志需要原始错误才能展开细节）；新增 `onSegmentFail` 回调，把「卡在第几段、前几段已合成」报给队列。
5. **`src/server.ts`**：接入 `FailureLog`；失败日志补充失败位置；任务最终判失败时强制完整展开细节；
   队列收尾增加失败原因分布统计与补转提示；`/api/progress` 增加 `errorHint`。
6. **文档**：`.env.example` 与 README 增加 `TTS_OUTAGE_WARN_AFTER` 与「失败日志怎么看」章节。

## 验证（接口宕机，用 stub 跑通全链路）

在临时目录复制一份工程、stub 掉 MiMo 域名的 fetch，真跑管线（拆句 → 逐段合成 → ffmpeg 合并 → 落盘）
与队列（重排队 / 补转 / 失败判定）：

| 场景 | 预期 | 结果 |
|------|------|------|
| 正常返回音频 | 完成、产出 mp3 | ✔ 真实 ffmpeg 合并出 5036 字节 mp3 |
| 前两次 500 后恢复 | 段级重试就地自愈 | ✔ 任务 `attempts=1`、`requeues=0` |
| 持续 500 | 段级 3 次 → 重排队 → 判失败，原文保留 | ✔ `requeues=1`，可补转 |
| 401 | 一次即判失败，不误重排队 | ✔ `requeues=0` |
| 200 但无音频 | 判为可重试 | ✔ 重试后判失败 |
| 网络中断（fetch failed / terminated） | 判为可重试，且打印底层原因 | ✔ |
| 失败后手动「重试失败任务」 | 补转成功、产出 mp3 | ✔ 接口返回 `requeued:1` |
| 日志体量 | 细节只展开一次 | ✔ 6 次接口失败，整轮 39 行 |

`npm run typecheck` 通过。

## 影响面与次生风险

- **只改了"打印什么"**：`retry.ts` 仅使用 `isRetryable`（语义未变），重试/重排队/补转的决策路径没动。
- `llm.ts` 不走这套错误分类，其失败仍按本地问题处理，行为不变。
- `/api/progress` 新增 `errorHint` 字段，前端未使用，纯增量，不影响现有 WebUI。
- 未做（已记入 README 已知限制）：接口整体宕机时没有熔断，每个文件仍会走完「段级 3 次 + 任务级 3 次」
  重试才判失败，只是比平时慢，不会丢文件；需要的话可加「连续失败 N 次即暂停队列」的开关。

## 备注（脱敏）

- 测试全程在 `/tmp` 的隔离副本里跑，`process.cwd()` 指向副本，未触碰工程的 `output/`。
  之所以不用真实工程目录起测试服务：服务启动时会清空 `output/.tmp`，会打断正在跑的队列。
- 未使用真实 Key 做批量压测；诊断用的最小请求直接读 `.env`，Key 未出现在日志、文档或 devlog 中。
- 日志默认不记录正文内容（小说内容不进日志），只记长度；仅 4xx 附 20 字片段用于定位。
