# 20260916 失败任务自动排到队尾重试

## 用户需求

小米 MiMo TTS 接口有一定几率返回不了内容（限流等原因），批量入队几十上百个文件时，中间常有几个失败，整批无法一次转完。希望加自动重试机制：**只有因 API 调用失败的文件**才自动加到队列末尾排队重试，本地原因导致的失败不重试。

## 小结

### 1. 错误分类（新增 `src/errors.ts`）

只有明确归为 API 侧故障的错误才允许重试：

- 可重试：429 / 408 / 409 / 425 / 5xx、请求超时、网络层中断、响应无音频数据、响应非合法 JSON
- 不可重试：400（请求本身有问题）、401（Key 无效/未配置）等其余 4xx，以及 ffmpeg 失败、暂存文件读不到、文本为空等本地原因
- 未识别的异常一律按本地问题处理（宁可少重试，不陷入无意义的重试循环）

### 2. 重试工具（新增 `src/retry.ts`）

`withRetry` + 指数退避 + 抖动（抖动避免同一时刻大量重试又齐齐打回接口），段级与任务级共用同一套退避算法。

### 3. 两层重试

- **段级**（`pipeline.ts`）：单段合成失败就地退避重试，默认总尝试 3 次。原来一段失败整章作废，200 段的章节在第 180 段挂掉要全部重来，这是最大的浪费点。
- **任务级**（`server.ts`）：整章仍失败且属 API 侧原因时，重新落一份暂存原文、把任务移到队列末尾，退避到点后再转；默认总尝试 4 次（最多重排队 3 次）。队列循环改为「跳过未到重试时间的任务」，只剩待重试任务时按 2s 间隔小睡，保证期间新入队的文件能及时插队。

### 4. 手动补转

重试上限内仍失败的任务停在「失败」，原文保留在内存，新增 `POST /api/queue/retry-failed` 与 WebUI「重试失败任务」按钮，可一键把失败任务重新排到队尾（换 Key / 接口恢复后补转）。

### 5. 其他

- mimo provider 补单次请求超时（`MIMO_TIMEOUT_MS`，默认 120s）：此前接口挂死会把整个队列永久卡住
- WebUI 队列列表区分「待重试」（标出第几次重试），状态行增加待重试计数
- 修掉接口健壮性问题：带 `Content-Type: application/json` 但无 body 的 POST 会被 Fastify 拒（`FST_ERR_CTP_EMPTY_JSON_BODY`），改为空 body 按 `{}` 处理
- 新增 7 个 .env 配置项（段级/任务级尝试次数与退避、请求超时），README 增「失败重试机制」章节

## 验证方式

临时脚本把 `globalThis.fetch` 换成假接口（不消耗真实额度），在隔离端口跑真实队列，覆盖：持续 429（重排队至上限后判失败）、401（一次即判失败不重试）、段级重试兜住恢复、任务级重排队兜住恢复、手动补转、多文件排队顺序（A 失败后确实排到 B、C 之后）。验证脚本与测试产物已删除，`output/` 数量还原。`npm run typecheck` 通过。

## 踩坑提醒

验证时脚本一度把请求打到了本机 5666 上正在跑的 dev server（而非测试端口），导致两个测试任务走了真实接口、并在 `output/` 留下测试产物。**后续写联调脚本必须用独立端口**（测试脚本改为读 `PORT`，与测试服务同端口）。另外 `tsx watch` 会在改动 src 时重启 dev server，用户队列为内存态、会随之清空。
